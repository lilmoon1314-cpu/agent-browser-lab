# Agent Browser Use 能力横测方法论（v0.1）

## 1. 为什么做这件事

市面上具备 Browser Use 能力（让 AI 操控浏览器替人完成任务）的产品和模型越来越多，但公开材料几乎只报一个"成功率"数字。要判断**Agent 到底能替人做什么、不能做什么、为什么做不到**，需要一套可复用的实测框架。本项目要回答三个问题：

1. 当前 Agent 在**真实网站**上的能力边界在哪里（哪些任务稳定完成、哪些靠运气、哪些完全不行）；
2. 失败发生在哪个环节（失败归因 = 场景挖掘和 Benchmark 设计的直接输入）；
3. 探针任务如何逐步升级为可自动化运行的 Benchmark。

## 2. 方法总览

```
设计探针任务 → Agent 真实执行 → 全程记录（截图/步数/耗时）→ 评分卡打分 → 失败归因 → 汇总机会点
```

四个设计原则：

- **真实**：任务来自真实人群的日常数字劳动，直接在真实网站上执行，不用模拟站点；
- **可验证**：每个任务预先定义"怎样算完成"，客观值核对（价格/评分/版本号）优先于主观判断；
- **可比**：所有 Agent 跑同一组任务、用同一张评分卡，结果才可横向对比；
- **安全**：所有任务**只读不写**——不登录、不下单、不支付、不发布任何内容。

## 3. 探针任务矩阵（12 个）

用两个维度组织任务：

- **难度**：L1 单页查找 → L2 多步交互 → L3 跨站聚合与异常处理
- **能力类型**：信息查找 / 表单交互 / 提取与总结 / 跨站聚合 / 歧义识别

| ID | 任务 | 难度 | 能力类型 | 完成验证方式 |
|----|------|------|----------|--------------|
| T01 | 豆瓣：查《置身事内》评分与评价人数 | L1 | 信息查找 | 客观值核对 |
| T02 | B站：查指定 UP 主最新视频标题与发布时间 | L1 | 信息查找 | 客观值核对 |

## 4. 评分卡

每次实验按统一评分卡记录，字段定义如下。

**结果主指标**

| 取值 | 判定标准 |
|------|----------|
| 成功 | 达到任务"完成定义"的全部要求 |
| 部分完成 | 到达目标页面/拿到部分正确信息，但未全部满足完成定义 |
| 失败 | 未拿到有效结果，或中途放弃/死循环 |

**过程指标**：步数、总耗时、异常次数（弹窗/验证码/加载失败等）。

**失败归因（五分类，结果为"部分/失败"时必填）**

| 代码 | 归因 | 典型表现 |
|------|------|----------|
| F1 | 规划错误 | 步骤顺序错、任务理解偏差、绕远路 |
| F2 | 元素定位错误（grounding） | 点错按钮、填错输入框、坐标偏移 |
| F3 | 信息提取错误 | 页面打开了，但读错/读漏内容 |
| F4 | 异常处理失败 | 遇到弹窗、验证码、加载失败后无法恢复 |
| F5 | 提前放弃 | Agent 自行判定"做不到"而停止 |

## 5. 实验记录规范

```
experiments/
└── 001-<agent>-<task-id>/        # 编号-agent-任务ID
    ├── README.md                 # 评分卡 + 过程简述 + 结论
    ├── 01-起始页.png              # 关键节点截图：起始页、关键操作、结果页
    ├── 02-xxx.png
    └── meta.json                 # 结构化字段，便于后续汇总统计
```

`meta.json` 字段：`experiment_id, date, agent_name, agent_version, task_id, status, steps, duration_min, anomalies[], failure_modes[], result_summary, screenshots[]`。

## 6. 局限性（v0.1 已知问题，诚实声明）

- **样本量小**：单次执行结果不构成统计结论，仅用于定性判断；重要结论需重复执行 ≥3 次；
- **人工评分有主观性**：客观字段（步数/耗时/异常次数）优先于主观字段；
- **真实网站会变化**：每个实验记录执行日期，不承诺跨日期可复现；
- **升级路线**：v0.2 起将探针任务改造为带自动验证器（checker）的 Benchmark 任务，实现无人值守跑分（见 ROADMAP）。
