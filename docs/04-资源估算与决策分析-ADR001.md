# T20 资源估算与决策分析（决策记录 ADR-001）

> 文档性质：决策记录（Decision Record）。写明背景、选项、数据依据、结论与放弃理由。
> 用途：① 作为 T20 立项依据；② 作为"如何做资源估算与决策"的方法示范；③ 面试被问"你为什么这样排期"时的原始凭据。

## 0. 待决策问题

T20「行业趋势跟踪助手」如何做、做多少、先做什么？
约束：1 人（本人，技术薄弱 + AI 辅助），每天可投入 2.5–4 小时，目标是为 Agent PM 实习投递积累可验证的证据。

## 1. 工程师视角：工作拆解与估算（WBS）

估算方法：**自下而上拆解 → 每项给乐观/悲观区间 → 参照本项目已有真实数据校准 → 取 P80 排期**。

参照锚（本项目已有实测数据，比任何经验公式都可靠）：
- experiment-001 全流程（设计+执行+归档+推送）：约 2 小时
- experiment-002（三角色重做+评分+归档）：约 1.5 小时
- 方法论文档 v0.1 + v0.2 修订：约 1.5 小时
- 结论：本人在 AI 辅助下，"设计+文档+轻量实验"类工作的真实速度 ≈ 1.5 小时/件；工程搭建类尚无实测数据，需加新手不确定系数。

| # | 组件 | 内容 | 乐观 | 悲观 | 主要风险 |
|---|------|------|------|------|----------|
| A1 | 冻结语料站 | 20 条虚构新闻（含时效/冲突两类干扰项）+ 静态页面 | 2h | 4h | 内容设计（非代码）占大头；AI 起草+人工把关可控 |
| A2 | mock 知识库 | 极简表格应用 + REST API + 本地运行 | 2h | 4h | 环境调试；警惕做成"真 Notion 克隆"的过度工程 |
| A3 | mock 邮箱 | 发送 API + outbox 查询 | 1h | 2h | 比 A2 简单（无复杂 UI） |
| A4 | checker ×4 | 金标准比对/库状态/outbox/端到端一致性 | 3h | 5h | 逻辑简单，边界情况（模糊标题匹配）耗时 |
| A5 | rubric judge | 评分脚本 + 10 份人工校准 | 3h | 5h | 校准一致率 <80% 需返工一轮 rubric |
| B1 | 横测执行 | 3 个 agent × 1–2 次（含测试账号准备） | 5h | 8h | **最大排期风险：live web 不稳定（flaky）** |
| B2 | 博客写作 | 结构+截图+评分表+叙事 | 4h | 6h | 写作量大但无技术风险 |
| | **MVP 合计** | | **20h** | **34h** | 取 P80 ≈ 30h 排期 |
| C1 | benchmark 化追加 | harness 自动化 + 重复运行 + 排行榜 | 15h | 25h | flaky 处理是无底洞，风险最高的一段 |

**换算成日历**（P80 = 30h）：每天 2.5h → 12 天；每天 4h → 8 天。C1 追加后全程 3–4 周。

**成本**：复用现有订阅（GLM Coding Plan）+ 开源工具 → ¥0 起步；若需另一家模型订阅一个月 +¥100–200；LLM judge 调用费 <¥10；无服务器（localhost/免费静态托管）。

**人力的正确理解**：1 人 + AI 的组合里，我的角色不是"写代码的人"而是"验收与决策的人"——AI 时代瓶颈从打字速度转移到判断速度，这正是该 JD 存在的原因。

**工程风险 Top3**：① live web flaky 拖垮排期 → 时间盒硬上限 + 失败本身记为数据；② mock 组件过度工程 → Done 标准写成"API 通 + 最小 UI"，到点即停；③ judge 校准不过 → rubric 从 5 维砍到 3 维重校，博客模式允许纯人工评分兜底。

## 2. 产品经理视角：目标重定义与价值排序

**第一问永远是：这个项目的"用户"和"成功标准"是什么？**
用户 = 面试官；成功标准 = 读完能记住我至少一个具体结论，且每个结论都可点开验证。**不是：工程完备的评测系统。** 目标一变，所有取舍跟着变。

**交付物价值排序**（对面试证据的贡献）：
1. 横测博客 —— 可见度最高，同时证明 JD 职责 1/3/4（行业追踪、Harness、数据驱动），且可传播
2. 方法论与角色分离协议（已完成 ✓）—— 区分度最高的深度证据
3. benchmark 排行榜 —— 最硬核但可见度低、工期最贵
4. mock 基础设施 —— 单独无价值，只是使能器 → **能简则简**

**砍功能阶梯（descope ladder）**——预算不够时按此顺序砍：
先砍：干扰项 4 类→2 类 → 参赛 agent 3→2 → 跨 SaaS 3 个→2 个
再砍：重复运行 2 次→1 次 + 失败案例定性分析
**永不砍**：角色分离协议、checker、rubric 校准披露——方法论完整性是本项目的灵魂，砍了它一切证据贬值。

## 3. 三个方案

| | 方案 A：博客优先 MVP（推荐） | 方案 B：benchmark 全量优先 | 方案 C：纯博客（不自建环境） |
|---|---|---|---|
| 内容 | A1–B2 全做，C1 仅留设计 | 先 C1 后博客 | 真实 SaaS + 人工评分，不做 mock/checker |
| 工期 | ~2 周（P80） | 3–4 周 | ~1 周 |
| 产出 | 横测博客 + 环境雏形 + 决策记录 | 排行榜（博客延后） | 快速博客，无 benchmark 证据 |
| 风险 | 低（flaky 有时间盒） | 高（最 flaky 的部分最先做） | 丢 JD 职责 2 的核心证据 |
| 适配 | 兼顾可见度与深度 | 投递窗口充裕且主打技术深度 | 投递窗口 ≤10 天时的应急 |

## 4. 决策与依据

**决策：选方案 A**，并在第 7 天设检查点（环境组件 A1–A5 是否全部跑通；未通则触发降级：砍 A3 mock 邮箱→用现成邮箱测试账号，砍重复运行）。

**依据清单（决策时看的数据）**：
1. 历史耗时：本项目 3 件已完成工作的实测工时（锚定真实速度，替代拍脑袋）
2. JD 证据覆盖：职责 1/2/3/4 对照表——方案 A 四条全覆盖，方案 C 缺职责 2
3. 依赖方向：benchmark 需要 judge 校准数据，校准数据来自博客模式的人工评分 → 博客在前是依赖决定的，不是偏好
4. 风险分布：方案 B 把最不确定的部分放在关键路径最前面，违反"先做能确定做完的"原则
5. 截止反推：目标投递窗口 4–6 周后 → 方案 A 留有 2 周缓冲准备简历与面试叙事，方案 B 无缓冲

**放弃方案 B 的理由（记录在案）**：排行榜证据强但可见度低，且把最高风险（flaky）放在最前面；若第 7 天检查点大幅提前，升级为 A+B 串行。

## 5. 可复用的方法论（带走的能力）

**估算三法**：① 自下而上 WBS（拆到 0.5–1 天颗粒）② 参照锚定（用自己/团队的实测历史，永远优于直觉）③ 区间思维（乐观/悲观 + P80 排期；新手对新类工作 ×1.5–2 系数）。接受"估算必然不准"，用区间和检查点让它无害。

**决策五步**：重定义目标（用户是谁/成功标准）→ 列选项 → 四维打分（价值/成本/风险/时机）→ 设检查点 → 写下决策与放弃理由（决策记录）。

**数据依据清单**（下次直接套用）：历史实测耗时 / 组件数与集成点数（集成点是成本黑洞）/ 外部依赖稳定性 / 依赖方向（谁必须在谁前面）/ 截止日期反推 / 目标对齐度（JD 对照）。
